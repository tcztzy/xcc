# AOT Python Strong Bootstrap Design

Status: revised 2026-07-11. This design supersedes the earlier interpretation
that a Python-hosted build of a native C compiler, or a successful CPython C
build, constitutes AOT Python self-hosting.

## Goal

Keep XCC as ordinary CPython 3.11+ source while compiling a documented strict
subset of that source directly to native code. The final compiler must strongly
self-host: Stage 0 builds native Stage 1, Stage 1 reads the repository's `.py`
files and builds Stage 2, and Stage 2 reads the same source and builds Stage 3.

Stage 1 and Stage 2 must not load or start CPython, link libpython, use the
Python C API, call `ast.parse`, or require a checked-in/generated AST or IR.
LLVM `llc`, the system assembler, and the system linker remain allowed tools.

No custom syntax, marker decorator, pragma, comment directive, or annotation
directive is introduced. Width aliases such as `int32`, `int64`, `uint64`, and
`usize` remain ordinary Python-visible aliases or annotations.

## Terminology

- **Hosted AOT**: CPython executes `xcc.aot` to parse, bind, lower, and emit a
  native artifact.
- **Native C compiler artifact**: native code generated by hosted AOT whose
  entry compiles C source. This is the current `build/aot/xcc` capability.
- **Native AOT compiler**: native code whose entry reads Python source and runs
  the Python-subset frontend, binder, lowerer, AOT IR emitter, and tool driver.
- **Strong self-hosting**: native Stage 1 builds Stage 2 from `.py`, then native
  Stage 2 builds Stage 3 from the same `.py` source set.
- **Admission**: hosted syntax/type preflight. Admission is not reachability,
  native execution, or self-hosting.

## Stage Model

### Stage 0

Stage 0 runs under CPython 3.11+. It may use `ast.parse`, but only through a
hosted adapter that converts CPython AST nodes to the project-owned AOT AST.
The binder and lowerer consume the project-owned AST, not CPython AST directly.

Stage 0 builds `build/aot/stage1/xcc-aot`.

### Stage 1

Stage 1 is the first native AOT compiler. It:

1. opens the declared repository `.py` files;
2. tokenizes and parses them with the project-owned subset lexer/parser;
3. binds types and resolves the module/call graph;
4. lowers typed AST to AOT IR;
5. emits deterministic textual LLVM;
6. invokes only allowed native tools; and
7. links `build/aot/stage2/xcc-aot`.

Stage 1 has no hosted parser fallback. `--parser=cpython` is rejected in the
native executable.

### Stage 2

Stage 2 is built by Stage 1. It repeats the same source-driven process with
`--no-cache` to build `build/aot/stage3/xcc-aot`.

### Stage 3

Stage 3 is the stability witness. Stage 2 and Stage 3 must have equivalent:

- normalized LLVM for the strong-bootstrap compile set;
- exported symbols and ABI metadata; and
- observable behavior on the defined compiler/runtime fixture suite.

Bit-for-bit executable equality is not required because link metadata and load
addresses may vary. Every normalization rule must be explicit and tested.

## Hard Constraints

- Runtime source remains Python standard-library only under CPython.
- Produced stages have no CPython or libpython runtime dependency.
- `from __future__ import annotations` remains forbidden.
- GPL-derived source/tests remain forbidden.
- No CPython-specific C source path, macro, or filename shortcut is introduced.
- Generated AST, IR, LLVM, manifests, or code may accelerate a build but cannot
  be the only input path.
- Deleting all AOT caches must not prevent Stage 1->2 or Stage 2->3.
- Native C compiler and CPython `configure && make` checks are final secondary
  integration gates, not strong-bootstrap acceptance.

## Source Contract

The accepted source is a strict CPython subset. Every accepted construct has a
defined binder, IR, runtime, and error behavior. The contract includes the
constructs already needed and claimed by the project:

- modules, statically resolved package imports, classes, and dataclasses;
- functions, methods, positional/keyword-only parameters, and explicit return;
- assignments, annotated assignments, and fixed-arity unpacking;
- `if`, `while`, `for`, `break`, and `continue`;
- `try`, supported `except` handlers, `raise`, and `finally` forms admitted by
  the status ABI;
- statically typed tuple/list/dict/set operations and iteration;
- negative indexes and slices with CPython-compatible normalization;
- equality, ordering, membership, arithmetic, bitwise, and boolean operations;
- statically resolved calls, properties, and supported `isinstance` forms;
- strings, bytes, paths, enums, and fixed records needed by the AOT compiler.

Rejected features include dynamic import hooks, `eval`, `exec`, arbitrary
reflection, monkeypatching, metaclasses, escaping generators, async/coroutines,
and runtime class-layout mutation.

### Milestone 2 Frozen Syntax and AST Surface

The Stage 0 adapter has a fixed CPython 3.11 grammar oracle
(`feature_version=(3, 11)`). The active `src/xcc` source inventory currently
uses these 77 owned-node kinds:

```text
Add And AnnAssign Assert Assign Attribute AugAssign BinOp BitAnd BitOr BitXor
BoolOp Break Call ClassDef Compare Constant Continue Dict DictComp Div Eq
ExceptHandler Expr FloorDiv For FormattedValue FunctionDef GeneratorExp Gt GtE
If IfExp Import ImportFrom In Invert Is IsNot JoinedStr LShift List ListComp
Load Lt LtE Mod Module Mult Name Not NotEq NotIn Or Pass RShift Raise Return Set
SetComp Slice Starred Store Sub Subscript Try Tuple USub UnaryOp While With
alias arg arguments comprehension keyword withitem
```

This inventory is a parser-implementation target, not native reachability
evidence. The accepted grammar is the source-contract constructs above plus
ordinary comprehensions, f-strings, and statically known `with` forms used by
the active compiler source. Async nodes, `await`/`yield`, lambda, match,
`global`/`nonlocal`, delete, and unknown adapter nodes are rejected. Allowed
decorators are the ordinary Python decorators `dataclass`, `staticmethod`,
`classmethod`, `property`, and `cache`; `dataclass` may use literal-`True`
`frozen` and `kw_only` keywords only.

Milestone 3 implements that target with the hand-written `py_lexer.py` and
`py_parser.py`. The oracle compares semantic fields, UTF-8 spans, and ordered
child edges against `ast.parse -> cpython_ast_adapter` for every active source.
The common `module.parse_source` boundary now uses the owned parser; explicit
hosted CPython parsing remains available only through Stage 0 adapters and the
`parser-oracle` command.

Supported annotation grammar is names and dotted project types, `|` unions,
grouping parentheses, width aliases, `Iterable[T]`, `Sequence[T]`,
`list[T]`, `set[T]`, `frozenset[T]`, `dict[K, V]`, fixed/variadic/empty
`tuple[...]`, `Callable[[...], R]`, and string-valued `Literal[...]`.
Numeric/bool `Literal` is rejected because its native type semantics is not the
string layout. String forward references use this same grammar without calling
CPython's parser.

Owned AST nodes have immutable tuple child fields. `span`, `text`, and
`children` are constructor inputs, so the project parser can create complete
nodes without mutation or CPython APIs. `children` must contain the same owned
nodes as the typed fields in field order. `text` is nonsemantic source/oracle
metadata: binder, lowerer, keys, and diagnostics use the structural renderer
and must behave identically when `text` is empty. `Constant.value` is limited by
the parser contract to `None`, bool, int, float, complex, str, bytes, or
ellipsis; `UnsupportedNode` and its opaque payload are adapter diagnostics and
are rejected before the native common path.

Source spans use 1-based lines, 0-based UTF-8 byte columns, and end-exclusive
end positions, matching CPython AST rather than Unicode code-point columns.
Owned lexer/parser diagnostics use the same convention, and hosted token/AST
oracles normalize their character columns before comparison.

### Milestone 2 Module, Manifest, and Cache Contract

`--source-root` names one package directory and `--entry` must name a module
inside it. Resolution reads strict UTF-8 bytes once, hashes those exact bytes,
and retains the decoded source and owned AST used downstream. It recursively
collects static imports anywhere in the owned tree, includes every parent
package `__init__.py`, rejects unknown external import roots, records allowed
stdlib roots separately, and orders project modules dependency-first. Strongly
connected components and members within a component use lexical order.

The canonical JSON manifest is version 1. Each unit records module identity,
root-relative and canonical paths, raw-byte SHA-256, project dependencies,
allowed external dependency roots, and deterministic order. It also records
the parser backend and cache policy. Parser kind and callback travel as one
`ParserBackend`; a caller cannot independently label a CPython callback as the
subset backend. The subset backend rejects `xcc.aot.__main__`,
`xcc.aot.hosted_cli`, `xcc.aot.cpython_ast_adapter`, and
`xcc.aot.parser_oracle` as explicit Stage 0-only modules.

Milestone 2 has no persistent AST/IR cache: reads and writes are both disabled.
The manifest records whether `--no-cache` was explicitly requested. A later
cache implementation may add an enabled policy, but `--no-cache` must always
force zero cache reads and writes and preserve source-file opens.

Normalized LLVM removes the declared source root only from nonsemantic LLVM
metadata (`ModuleID`, `source_filename`, and `DIFile`) and trims trailing line
space. It must not rewrite global constants, function bodies, symbols, or other
program data containing the same path text.

### Native Operation Inventory and Ownership

| Layer | Required operations | Current state | Native closure |
|---|---|---|---|
| CLI contract | argv tuple indexing, string split/prefix/membership, option state, deterministic status/diagnostic | Native contract shell lowers and links; hosted mode exposes CPython/subset builds plus `parser-oracle`; native rejects CPython parser | Full native build dispatch remains M5 |
| source loader | canonical path checks, strict byte reads/UTF-8 decode, parent/import closure, SCC order | Contract and hosted implementation complete | Native path/read intrinsics remain M5 |
| manifest | raw SHA-256 and canonical JSON | Hosted implementation complete and bound to the same source snapshot | Owned hash/JSON writer or native shims remain M5 |
| frontend | indentation/token/literal scanning and owned-node construction | Owned immutable AST, hand-written lexer/parser, stable rejection diagnostics, and CPython oracle complete | M3 proves hosted subset source closure only; emitted native call-graph closure remains M5 |
| common compiler | walk/structural render, subset validation, binding, typed lowering, IR text emission | Public binder/lowerer APIs consume only owned AST | Emitted call-graph closure remains M5 |
| runtime/error | strings/bytes/path, tuples/lists/maps/sets, allocation, status/error propagation | Existing assets only; known semantic gaps remain | Status ABI/runtime work remains M4 |
| tools | write LLVM/assembly/object, invoke configured `llc`, optional assembler, and linker command, check status | Hosted runner accepts explicit paths | Native spawn/file boundary and audit remain M5/M6 |

`pathlib`, `hashlib`, `json`, and `subprocess` imports in the hosted
implementation are therefore not evidence that equivalent native operations
already exist. All-source admission checks syntax and types only. A configured
linker command may be a system compiler driver such as `cc`; the audit treats
that single configured command as the linker boundary and still rejects any
Python executable.

For an accepted construct, changing ordinary XCC core source to avoid a
lowerer/runtime bug is not a valid implementation. The binder, lowerer, or
runtime must be fixed. A core source rewrite is allowed only when the construct
is explicitly excluded, the rewrite is smaller than implementing it, and
CPython behavior plus native behavior are both covered by oracles.

## Frontend Architecture

Both hosted and native modes converge immediately on a project-owned AST:

```text
Stage 0 only
  source -> CPython ast.parse -> cpython_ast_adapter -> XCC-Python AST

Stage 0 oracle and Stage 1/2/3 required path
  source -> py_lexer -> py_parser -> XCC-Python AST

Common path
  XCC-Python AST -> subset validation -> binder -> typed AST -> AOT IR
```

### Project-Owned AST

`src/xcc/aot/py_ast.py` owns fixed dataclass-like node types, source spans,
operators, annotations, imports, statements, and expressions. It has no
dependency on CPython `ast` classes. Nodes must themselves be representable in
the accepted subset so the frontend can compile itself.

### Hosted Adapter

`src/xcc/aot/cpython_ast_adapter.py` is Stage 0-only. It maps CPython AST to the
project-owned AST and preserves line/column spans. It is an oracle and a first
bootstrap convenience, not part of Stage 1 reachability.

### Subset Lexer and Parser

`py_lexer.py` and `py_parser.py` implement only the documented grammar. They are
hand-written, deterministic, and written in the same subset. A generated parser
table may be cached for development, but native stages must be able to rebuild
and run without it.

The parser oracle compares normalized project-owned ASTs from:

```text
CPython ast.parse -> adapter
project-owned lexer/parser
```

for every accepted syntax fixture and every repository module in the active
compile set. Rejection fixtures compare stable diagnostic code and source span.

## Module and Reachability Model

The compiler resolves only the declared source root and allowed stdlib shims.
Imports are canonicalized to module identities; module initialization order is
deterministic. Dynamic import is rejected.

Native compile reachability is separate from admission. The Stage 1 call graph
must include at least:

- AOT CLI and source loader;
- project-owned lexer/parser and AST constructors;
- subset validation and binder;
- typed-AST to AOT-IR lowerer;
- AOT IR data model and textual LLVM emitter;
- native runtime and allowed tool invocation boundary.

A gate checks the emitted graph and native symbols. Merely parsing every source
file under CPython does not satisfy this requirement.

## Type and Binding Model

The binder consumes project-owned AST. Function ABI boundaries require explicit
annotations or a deterministic inference rule. Dataclass fields and compiler
records have fixed layout. Local inference is allowed only when every control
path produces one supported static type.

Width aliases are compile-time facts layered on ordinary Python aliases. Plain
`int` uses the documented subset semantics; exact-width aliases lower to fixed
LLVM integer types. Optional and union values have explicit layouts and control
flow, not untagged pointer guesses.

The binder resolves calls and method receivers before lowering. Protocol-like
interfaces must carry concrete layout/dispatch evidence; function-name rewrite
tables and empty protocol stubs are migration scaffolding, not final semantics.

## AOT IR

AOT IR is independent of both CPython AST and the C compiler AST. It represents:

- deterministic modules and initialization;
- typed functions/methods and fixed records;
- primitive, string, bytes, path, option, tuple, list, and map values;
- structured and explicit control flow;
- allocation/lifetime operations;
- fallible calls, status branches, handlers, and error propagation; and
- external tool/runtime boundary calls.

IR validation runs before LLVM emission. Invalid SSA, missing branch values,
unresolved calls, unhandled fallibility, or unsupported dynamic values are hard
errors with deterministic diagnostics.

## Exception and Status ABI

Python source retains ordinary `raise`, `try`, and `except`. Native lowering
uses explicit control flow.

Fallibility analysis marks every function that can raise or call a fallible
function. A fallible internal function ABI is:

```text
status fn(args..., result_out, error_out)
```

- status `0` means success and initializes `result_out` when non-void;
- nonzero status means failure and initializes `error_out`;
- an error object carries a stable type tag, message, source location, and
  optional typed payload;
- every fallible call branches immediately on status;
- a matching handler consumes the error and continues at its handler block;
- a nonmatching handler returns the same status/error to its caller; and
- only the outer CLI converts an uncaught error to diagnostics and process exit.

`IrRaise -> exit(2)` is accepted only as a temporary safety measure for a CLI
top-level path. It cannot appear as the implementation of general `raise` or a
callee that may be covered by `try/except`.

## Runtime Model

The runtime is small and project-owned. It does not emulate the full CPython
object model. Required semantics include:

- fixed record headers/type tags and deterministic field layout;
- length-aware UTF-8 strings and byte arrays;
- immutable tuples and mutable typed lists;
- typed hash maps/sets with value equality and key hashing;
- normalized negative index and slice behavior;
- path values with canonical value equality;
- deterministic iteration and mutation rules used by the compiler;
- arena or explicit ownership with no dangling cross-phase values;
- file/source reads and an allowlisted process/tool boundary; and
- explicit error objects/status propagation.

Pointer identity may implement `is None` and documented singleton/type-tag
tests. It cannot substitute for supported string, tuple, path, or dict equality.

## Hosted and Native CLI

The same ordinary Python command contract is exposed in hosted and native form:

```text
python -m xcc.aot build [options]
xcc-aot build [options]
```

Required options include:

- `--source-root PATH`
- `--entry MODULE:FUNCTION`
- `--output PATH`
- `--parser=cpython|subset` in hosted mode
- `--parser=subset` only in native mode
- `--no-cache`
- `--emit-llvm PATH`
- `--emit-normalized-ir PATH`
- `--source-manifest PATH`
- configured `--llc`, assembler, and linker paths

The source manifest records canonical input path, content hash, module identity,
and dependency order. Acceptance builds use `--no-cache` and independently
audit source-file opens; the manifest is evidence, not the sole proof.

## External Tool Boundary

Native stages may spawn only configured `llc`, assembler, and linker commands.
The platform C runtime is allowed. Python executables and dynamic libpython/Python
C API loading are forbidden.

The acceptance harness uses a platform exec/open audit shim (Darwin
`DYLD_INSERT_LIBRARIES`, Linux `LD_PRELOAD`, or an equivalent syscall tracer) to
record child execs and source opens. The audit runs around Stage 1->2 and Stage
2->3; Python may inspect the log only after those native build processes have
completed, not as a parent required by the build.

## Determinism and Caches

Compiler ordering is explicit for files, modules, records, functions, globals,
and string constants. Normalized IR removes only declared nondeterminism such as
absolute build roots and nonsemantic module identifiers.

Acceptance deletes stage caches and generated AST/IR inputs before each native
build. Stage outputs may include fresh diagnostics, manifests, and LLVM, but the
only semantic source input is the declared `.py` set plus static configuration.

## Verification Strategy

Verification is layered:

1. lexer token oracle against Python tokenization for the accepted grammar;
2. parser AST oracle against `ast.parse -> adapter` under Stage 0;
3. binder/type oracle on repository modules and focused snippets;
4. AOT IR validation and normalized hosted/native IR comparison;
5. runtime CPython/native behavior fixtures for each accepted construct;
6. native reachability/symbol gate for the AOT compiler itself;
7. Stage 0->1, Stage 1->2, and Stage 2->3 builds;
8. no-libpython/no-Python-process/source-open audits;
9. Stage 2/3 normalized IR, symbol, and behavior equivalence; and
10. final Python tests, native C compiler smoke, CPython `configure && make`,
    lint, and type checks.

All-source admission remains a useful preflight but proves only that hosted
parsing/checking accepts the files.

## Source Change Policy

Every change outside `src/xcc/aot` made for AOT must be recorded with:

- exact reason and failing source shape;
- whether the construct is accepted or rejected by the subset;
- why an AOT-owned fix is insufficient if core source changes;
- CPython oracle command/result;
- native oracle command/result; and
- commit containing only that behavior.

Source-text assertions are supplementary. They do not prove semantic parity.
The current worktree ledger and unresolved mixed files are documented in
`2026-07-11-aot-python-strong-bootstrap-audit.md`.

## Migration From Current State

The current binder, lowerer, IR, emitter, runtime helpers, native tool runner,
tests, and C compiler integration are retained as assets. Migration proceeds by:

1. freezing and splitting the current hosted Stage 0 work;
2. introducing the project-owned AST and CPython adapter;
3. migrating binder/lowerer APIs off CPython AST;
4. implementing the subset lexer/parser and status ABI;
5. adding the native AOT CLI root and reachability gate;
6. producing Stage 1, then Stage 2, then Stage 3; and
7. returning to C/CPython build integration only after strong bootstrap gates.

No current result needs to be deleted to make this correction. Temporary layers
remain clearly labeled until replaced and covered by stronger gates.

## Acceptance Criteria

The design is complete only when all are proven:

- Stage 0 builds native Stage 1.
- Stage 1 reads repository `.py` source and builds Stage 2 without executing or
  loading Python and without relying on pre-generated AST/IR.
- Stage 2 reads the same `.py` source and builds Stage 3 under the same rules.
- `otool`/`ldd` and `nm` show no libpython or Python C API dependency for native
  stages.
- exec/open audit shows no Python process and shows actual `.py` source reads in
  Stage 1->2 and Stage 2->3.
- native reachability includes the subset parser, binder, lowerer, IR emitter,
  runtime boundary, and AOT CLI.
- Stage 2 and Stage 3 have equivalent normalized IR, exported symbols, and
  required behavior fixtures.
- the project remains a normal CPython 3.11+ project.
- no custom syntax, marker decorator, pragma, or comment directive exists;
  width aliases remain ordinary Python annotations/aliases.
- relevant full tests, `uv run tox -e lint`, and `uv run tox -e type` pass.
- native C compiler smoke and CPython `CC="xcc" ./configure && make` pass as
  final secondary integration gates.
